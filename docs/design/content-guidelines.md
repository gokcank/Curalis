# Content Guidelines

## Purpose

This document defines the writing standards, terminology, and communication principles used throughout Curalis.

Its purpose is to ensure that every piece of text feels consistent, trustworthy, accessible, and medically appropriate.

These guidelines apply to:

- User Interface
- Notifications
- Dialogs
- Errors
- Empty States
- Help Content
- Onboarding
- Settings
- Documentation presented inside the application

---

# Writing Philosophy

Language should help users complete tasks with confidence.

Writing should always be:

- Clear
- Concise
- Respectful
- Neutral
- Human

Avoid unnecessary technical language.

---

# Voice

Curalis speaks like a calm and knowledgeable assistant.

The application should never sound:

- robotic
- sarcastic
- playful
- dramatic
- overly enthusiastic

Professional does not mean cold.

Friendly does not mean casual.

---

# Tone

Tone should adapt to context while remaining consistent.

Examples:

Information

→ Neutral

Reminder

→ Calm

Success

→ Reassuring

Warning

→ Attentive

Error

→ Helpful

Critical Alert

→ Clear and direct

---

# General Principles

Prefer:

- short sentences
- familiar words
- active voice
- direct instructions

Avoid:

- jargon
- marketing language
- unnecessary adjectives
- emotional manipulation

---

# Medical Responsibility

The application describes information.

It does not interpret it.

Avoid wording that could be understood as medical advice.

Example

Good

"Reminder completed."

Bad

"Treatment completed successfully."

---

# Terminology

Always follow the terminology defined in:

glossary.md

Do not invent alternative terms.

Consistency improves comprehension.

---

# Buttons

Buttons should describe the action.

Good examples:

Add Medication

Save Changes

Confirm Reminder

Export Data

Avoid generic labels such as:

OK

Continue

Submit

Done

unless context makes them completely unambiguous.

---

# Dialog Titles

Titles should summarize the purpose.

Examples:

Delete Medication

Discard Changes

Grant Notification Permission

Avoid vague titles.

---

# Dialog Content

Dialog text should answer:

- What happened?
- Why?
- What happens next?

Keep dialogs concise.

---

# Error Messages

Error messages should include:

- what happened
- what users can do next

Avoid exposing technical details.

Example

Good

"Couldn't load medication information. Please try again."

Bad

"Exception 502."

---

# Success Messages

Success messages should confirm completion.

Examples:

Medication added.

Reminder updated.

Backup completed.

Avoid exaggerated celebration.

---

# Warning Messages

Warnings should explain risk without creating unnecessary anxiety.

State:

- what needs attention
- why
- recommended action

---

# Empty States

Empty states should educate and encourage.

Every empty state should include:

- explanation
- next step

Avoid blame.

---

# Notifications

Notifications should be timely, actionable, and concise.

Avoid sending notifications that do not require user attention.

---

# Forms

Labels should remain visible.

Placeholder text should never replace labels.

Helper text should explain—not repeat—the label.

---

# Dates & Times

Dates and times should follow the user's regional preferences.

Avoid ambiguous date formats.

Use relative dates only when they improve clarity.

Examples:

Today

Tomorrow

Yesterday

---

# Numbers

Numbers should prioritize readability.

Examples include:

Medication quantity

Remaining days

Reminder count

Inventory

Use grouping separators where appropriate.

---

# Units

Always display units.

Examples:

mg

mL

tablet

capsule

Never assume users understand values without units.

---

# Capitalization

Use sentence case throughout the interface unless platform conventions require otherwise.

Avoid unnecessary capitalization.

---

# Punctuation

Use punctuation only when it improves readability.

Avoid excessive punctuation.

---

# Abbreviations

Avoid abbreviations unless they are widely understood within the medical context.

Prefer complete words whenever practical.

---

# Localization

Write source text that is easy to translate.

Avoid:

- idioms
- wordplay
- cultural references
- slang

---

# Accessibility

Writing should remain understandable for users with varying reading abilities.

Prefer plain language whenever practical.

---

# Inclusive Language

Use language that respects all users.

Avoid assumptions about:

- age
- gender
- culture
- medical condition
- technical knowledge

---

# AI Generated Content

AI-generated text must follow these guidelines before being presented to users.

Generated content should always remain:

- factual
- neutral
- medically responsible
- clearly distinguishable from verified information when appropriate
